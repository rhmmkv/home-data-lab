# Воспроизведение анализа

Расчёты рассчитаны на PostgreSQL и схему `olist`. Ниже описан запуск в существующей Docker-среде лаборатории. При другой конфигурации нужно адаптировать имя сервиса, роли, базу и путь к CSV в скрипте импорта. Развёртывание сервера с нуля не автоматизировано.

## 1. Подготовить среду и данные

- PostgreSQL 18 с базой `home_data_lab` и ролью `lab_admin`, имеющей право создавать в ней схему.
- Существующая роль `analyst`, которой SQL создания таблиц выдаст права чтения.
- Для приведённых команд: сервис Compose `database`, доступный из каталога запуска `docker compose`.
- Девять исходных CSV из [набора Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), распакованные в `/srv/data/datasets/olist/csv`.

Скопировать каталоги `sql/` и `scripts/` рядом с действующим Compose-файлом PostgreSQL. Состав CSV, ожидаемые количества строк и контрольные суммы — в [описании данных](../data/README.md).

## 2. Создать таблицы и загрузить CSV

Из каталога с Compose-файлом выполнить:

```bash
sudo docker compose exec -T database \
  psql -X -v ON_ERROR_STOP=1 -U lab_admin -d home_data_lab \
  < sql/olist/01_create_tables.sql

bash scripts/import_olist.sh
```

SQL создаёт пустую схему и таблицы, затем выдаёт `analyst` права чтения. Он предназначен для первичной подготовки; повторный запуск поверх существующей схемы завершится ошибкой.

Скрипт проверяет наличие файлов и отсутствие строк во всех целевых таблицах, затем загружает их через `COPY FROM STDIN` и показывает сверку количества строк. Каждый CSV загружается отдельной транзакцией. При сбое ранее загруженные таблицы сохранят данные; причину сбоя и состояние таблиц нужно проверить до повторного импорта. Автоматическая очистка таблиц не выполняется.

## 3. Проверить загрузку и свойства данных

В DBeaver либо `psql` выполнить:

| SQL | Назначение |
|---|---|
| [02](../sql/olist/02_verify_counts.sql) | Сверка количества строк девяти таблиц с исходными CSV |
| [04](../sql/olist/04_orders_initial_checks.sql) | Уникальность заказа и пропуски ключевых полей |
| [05–07](../sql/olist/README.md) | Период данных, месячные и дневные количества, состав статусов |
| [08](../sql/olist/08_delivery_dates_by_status.sql) | Статусы и наличие фактической даты доставки |

Ожидаемые результаты и их значение — в [проверках данных](../analysis/olist/data_quality.md). Соответствие числа строк проверяет полноту импорта этих файлов, но не полноту покрытия бизнеса выгрузкой.

## 4. Повторить основные расчёты

| Порядок | SQL | Ожидаемый результат |
|---|---|---|
| 1 | [09 — доля опозданий](../sql/olist/09_delivery_lateness_rate.sql) | 6 534 из 96 470; после округления 6,77% |
| 2 | [10 — медианная задержка](../sql/olist/10_delivery_lateness_median.sql) | 7 календарных дней |
| 3 | [11 — последние отзывы](../sql/olist/11_latest_order_reviews.sql) | 98 673 строки и столько же уникальных заказов |
| 4 | [12 — проверка соединения](../sql/olist/12_delivery_reviews_join_checks.sql) | 96 470 строк и уникальных заказов; 95 824 с оценкой |
| 5 | [13 — сравнение оценок](../sql/olist/13_delivery_reviews_comparison.sql) | Две группы, значения из [отчёта](../analysis/olist/REPORT.md) |

SQL 09, 12, 13 и 15 используют границу следующего дня после предполагаемой даты. Для исходного набора предполагаемая дата имеет время `00:00`; определение соответствует сравнению календарных дат в SQL 10 и 14. При замене данных нужно проверить это условие и уникальность последних отзывов: равные максимальные времена ответа могут дать несколько строк на заказ.

Все результаты относятся к исходному набору из `data/sources.json`, без дополнительного временного фильтра. Для проверки в DBeaver достаточно роли `analyst` с правами чтения.

## 5. Собрать дашборд

Запустить Metabase по [инструкции инфраструктуры](../infra/metabase/README.md), затем создать вопросы из SQL 14–15 и расположить карточки по [описанию дашборда](../analysis/olist/dashboard.md).

Сохранённые вопросы и настройки хранятся в служебной базе Metabase. Инструкция описывает ручную сборку; автоматический импорт дашборда не предусмотрен.

## 6. Повторить анализ версии 0.2

[Ноутбук](../analysis/olist/notebooks/01_delivery_reviews.ipynb) читает таблицы `orders`, `order_reviews`, `order_items` и `products` из той же базы ролью `analyst`.

Версии, на которых получены результаты: Python 3.14.6, pandas 3.0.3, NumPy 2.4.6, SciPy 1.18.0, statsmodels 0.14.6, SQLAlchemy 2.0.51, psycopg 3.3.2 (окружение Anaconda).

1. Открыть SSH-туннель к PostgreSQL на локальный порт `15432`. При другом адресе или порте нужно изменить строку подключения в первой ячейке.
2. Записать пароль роли `analyst` в `~/.pgpass` с правами `600`. Строка подключения пароль не содержит.
3. Выполнить ноутбук сверху вниз.

Первые ячейки повторяют числа версии 0.1: 96 470 заказов, 6 534 опоздания, 95 824 заказа с оценкой. Остальные ожидаемые значения приведены в [отчёте v0.2](../analysis/olist/REPORT_v0.2.md).
